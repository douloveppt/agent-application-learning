# 第 29 章离线实验：共享预算、受限升级与私有结果缓存

本实验只使用 Python 3.11+ 标准库，不联网，不访问模型、账单或工单系统。模型能力、质量检查与用量均为预先设定的教学数据，**不能用输出推断真实模型质量、延迟、价格或供应商计费语义**。`microcredits` 是整数教学费用单位，不对应货币。

## 运行

在本目录执行：

```bash
python3.11 lab.py
python3.11 -m unittest -v test_lab.py
```

如果本机 `python3` 已是 3.11 或更高版本，也可替换命令中的解释器。输出为 JSON；测试不需要任何密钥。

## 按这个顺序读输出

| 输出字段 | 应观察到什么 | 说明 |
| --- | --- | --- |
| `upgrade` / `upgrade_ledger` | `small-eu` 后升级 `strong-eu`，实际共花 110，剩余预留为 0 | 先按地域与能力硬筛选；低价但不合规的候选不参与排序；每次尝试单独预留 |
| `same_scope_cache` / `other_tenant_cache` | 前者 `cache_hit`，后者 `null` | 同一可信权限与版本范围可以复用；不同租户不能命中 |
| `upgrade_budget_denied` | `budget_exhausted`，只有一次尝试 | 上限 120；首轮实际 30，剩余 90，无法覆盖升级预留 100 |
| `timeout_before_reconciliation` | `spent=0`、`reserved=40`，条目为 `unknown` | `spent=0` 只代表尚无已确认用量，不能宣称此次调用免费 |
| `timeout_after_reconciliation` | `spent=25`、`reserved=0` | 明确对账后结算 25；未知状态不能通过普通 `settle` 假装已确认 |
| `unknown_effect_blocks_fallback` | `reconciliation_required`，只有一次尝试 | 用模拟标志演示外部写入未知时停止升级；实验没有执行实际写入 |
| `confirmed_write_is_not_replayed` | `write_effect_confirmed`、`quality_state=failed`，只有一次尝试 | 写入事实已确认，答复质量不通过也不能重复写入 |
| `actual_usage_overrun_is_not_clamped` | `spent=55`、`overrun=15`、`admission_blocked=true` | 保留完整实际用量；预估不足不能通过截断实际费用掩盖 |

只读任务最多选两个合格候选，即初始一次、升级一次；非只读任务最多派发一次，质量不通过也不自动重放。写入已确认时返回 `write_effect_confirmed` 并独立保留质量状态；未确认发生写入时返回 `write_effect_not_confirmed`，仍需显式业务协议决定后续。只读任务出现已确认副作用时返回 `effect_contract_breached`，不继续升级或写缓存。实验用预设的 `quality_pass` 演示门禁，**没有实现可信的生产质量判定器**；证据适用性、字段校验和效果评测需要另行建设。

## 代码里最值得看的四个边界

1. `Ledger.reserve()` 把“检查余额与增加预留”放在同一把锁里。12 个线程各申请 30、总上限为 100 时，只能接纳 3 个。正常估算合同下，`spent + reserved <= limit`。同键同额且仍为 `reserved` 时可幂等复用预留；`unknown`、`settled` 状态拒绝再次预留。**预算预留不代表一次性派发许可**，不能据此反复调用模型或业务系统。这是进程内原子性示范，不是多实例数据库实现。
2. `settle()` 与 `reconcile()` 记录完整实际用量，重复同值结算不重复扣费，异值结算报冲突。超时保留预留，直到明确对账。**如果真实用量超出预留，账本可以超过上限**；实验记录违约并阻止新准入。严格费用上限还需要适配器可执行的输出、工具与资源上限，以及足够保守的价格和用量估算。
3. `ResultCache.key()` 包含可信租户、用户、授权版本、请求、地域、能力、Prompt、证据、路由政策、输出 Schema、结果合同与模型配置版本。`model_config_version` 表示受控的模型候选集及其参数配置版本；候选或参数变化必须由服务端提升版本。它不是用户可伪造的声明。实验采用保守的用户级隔离，拒绝缓存业务写入结果。调用者必须先完成认证与当前权限校验；缓存键本身不是授权机制。真实数据变化还需要 TTL、失效通知、内容摘要、加密与审计。
4. `continuation_stop()` 在接纳前和调用结果后都检查取消与副作用事实。换模型不会撤销上一轮写入，取消也不会抹去已经产生的费用。`usage_state`、`effect_certainty`、`cancel_requested` 与 `quality_state` 分开记录；用量和业务结果同时未知时，返回核实状态且继续保留费用预留，不能让一个 `status` 丢掉另一种不确定性。已确认的副作用也必须保留，答复质量失败不能将它改成“没有执行”。

## 动手修改

- 把 `Ledger(150)` 改成 `Ledger(120)`，解释升级被拒绝时为何仍结算首轮 30。
- 给 `Task` 换一个 `authz_epoch` 或 `evidence_version`，确认旧缓存失效。
- 把首轮结果改为 `SimulatedOutcome(False, None)`，检查预留为何不能释放。
- 把首轮实际用量改为大于预留的值，观察完整实际用量和违约标志；不要把账本改成 `min(actual, reserved)`。
- 阅读并发测试，找出“先读余额、锁外扣款”的实现为什么会超卖。

## 到企业实现还缺什么

本实验没有持久化、跨进程事务、崩溃恢复、重启对账、真实认证、多维租户额度、全局并发限制、截止时间、供应商限流、价格目录、账单校准、TTL、缓存加密或生产评测。`Router` 只在本实例内限制 Run ID 调用一次，不是跨实例的一次性执行保证，也不支持恢复或重放；模型调用与账本更新之间的崩溃窗口需结合第 12、26 章的持久派发协议、幂等操作身份与核实协议处理。更换 Run ID、重新构建 Router 或复用仍为 `reserved` 的预留，都不能作为重放已派发操作的依据。

生产环境应持久保存预留身份与状态，在事务内更新预算，按受控适配器计算保守预留，并将实际供应商 usage 与账单定期核对。需要请求幂等、预留失效与孤儿核查、显式价格版本、共享总预算和业务操作账本；未知预留不可仅因租约到期而认定零用量。缓存访问控制与外部写入回执仍需独立验证。
