# 第 25 章实验：持久任务、租约与产物归属

员工提交一份“VPN 故障周报”任务。客户端重试接收请求、队列重复唤醒、Worker 崩溃重启时，服务要围绕同一个 Run 继续处理；旧 Worker 恢复后不能覆盖新 Worker 的结果。用户取消后，迟到结果不能发布。报告正式提交后，临时工作区销毁也不影响下载。

本实验使用 Python 3.11 标准库与 SQLite，所有行为在本机临时目录中发生，不调用模型、消息队列、对象存储或外部业务系统。`Store` 是应用服务层教学接口，没有启动 HTTP 服务。演示结束自动销毁它自己创建的临时目录。

## 运行与预期结果

在本目录执行：

```bash
python3.11 backend_lab.py
python3.11 -m unittest -v
```

演示输出：

```text
1 持久接收：created=True，重复请求复用任务=True
2 重复唤醒：无额外领取=True
3 租约回收：epoch=1→2，旧 Worker 回写被拒绝
4 工作区销毁：exists=False，正式产物仍可下载=True
5 跨租户下载：拒绝
6 运行中取消：cancel_requested
  迟到产物提交：拒绝
  Worker 确认后：cancelled
```

18 项场景测试应全部通过。测试使用 `TemporaryDirectory` 隔离数据，并以可控时钟推进租约，不依赖实际等待。并发测试使用 6 个线程分别打开数据库连接竞争领取。

## 1. 先看服务契约

`Principal(tenant_id, user_id)` 代表已经经过认证的服务端身份。实验直接构造固定身份，**不实现认证，也不应接受客户端任意构造 Principal**。生产入口应从可信认证上下文获得身份，再执行权限检查。

| API | 用途 | 核心约束 |
| --- | --- | --- |
| `create_session(principal)` | 创建属于该员工的 Session | 会话归属由服务端记录 |
| `submit(principal, session_id, request_key, payload)` | 持久接收请求，返回 `(run_id, created)` | 先检查 Session 归属；同键同规范化请求复用 Run，不同请求冲突 |
| `get_run(principal, run_id)` | 查询状态与已提交产物引用 | 同时匹配租户、用户、Run；完成回执丢失时可找回 `artifact_id` |
| `claim(tenant_id, worker_id, lease_seconds=30)` | 可信调度器领取一个可运行 Run | 原子检查租户并发数，安装新租约与 epoch |
| `heartbeat(lease)` | 延长当前有效租约 | 核对 Run、租户、Worker、epoch、状态与数据库中的有效期 |
| `request_cancel(principal, run_id)` | 提交持久取消意图 | 排队任务立即取消；运行任务等待 Worker 确认或租约到期 |
| `acknowledge_cancel(lease)` | Worker 停止后确认 | 必须仍持有当前有效租约，状态为 `cancel_requested` |
| `complete(lease, content)` | 提交正式报告 | 同事务保存产物与成功状态；旧租约和取消状态不能提交 |
| `download(principal, artifact_id)` | 按稳定引用读取产物 | 重新检查租户与用户，并验证内容摘要 |

`claim()` 是内部调度接口，不是用户接口。拥有一个 `run_id`、`artifact_id` 或文件名不会获得权限；本实验对他人的 Session、Run、产物统一返回 `NotFound`。租户内其他员工占用了同一个请求键时，统一返回 `Conflict("request key unavailable")`，不泄露 Run、正文或正文是否相同。

## 2. 接收去重与调度领取是两层约束

`submit()` 将请求键、指纹和 Run 放入同一 SQLite 事务，数据库唯一约束是 `UNIQUE(tenant_id, request_key)`。`payload` 只允许一个 `topic` 字段，去掉其首尾空白后进行稳定 JSON 编码；指纹绑定 Session 与规范化正文。因此，`"weekly"` 与 `" weekly "` 被应用定义为同一请求，换 Session 或换主题会冲突。

生产键的作用域可以扩展为租户、调用主体、API 路由或动作类型等；必须事先定义，不能依赖调用方猜测。本实验保留全部请求键，不演示过期删除。若在生产删除去重记录，要分析客户端重试、事件重放与数据保留窗口，不能让旧请求重新产生新任务。

`claim()` 则从数据库寻找 `queued` 或租约已过期的 `running` 记录。消息只是“可能有工作”的唤醒提示；重复唤醒会再次检查数据库，不会直接获得运行权。实验没有真正的消息队列，也没有 Outbox，数据库中的未领取任务由后续 `claim()` 扫描发现。实际应用应实现周期扫描或可靠投递，避免只等待一次唤醒。

`max_open_runs` 默认 20，限制每租户处于 `queued/running/cancel_requested` 的任务总数；超过时拒绝新任务。已有请求的重复查询先于该限制执行，所以积压满额不会阻止客户端找回已接收的 Run。默认 `max_active=1`，限制每租户同时有效的运行／取消租约数。两个阈值都是便于观察的实验设置。

## 3. 租约到期不等于旧进程已经停止

每次领取都递增 `lease_epoch`。例如，Worker A 获得 epoch 1，超时后 Worker B 获得 epoch 2。A 即使迟到恢复，也不能通过 `heartbeat()` 或 `complete()` 更新该 Run。检查同时包含租户、Worker、epoch、当前状态与有效期；有效期采用半开区间，到 `lease_until` 时即失效。

心跳和完成都必须在获得数据库写事务之后读取时钟，不能使用等待数据库锁之前的旧时间复活已过期租约。`Lease.expires_at` 只是领取时的快照，服务始终以数据库里的租约为准。`ManualClock` 只是测试依赖，生产应采用统一时间来源并分析时钟偏移。

租约约束的是**合法执行权**。到期的旧 Worker 仍可能占 CPU 或执行已发出的请求，因此有效租约数不等于实际进程数、外部调用数。本实验没有运行真正的后台 Worker，也不证明外部动作恰好发生一次。生产仍需执行环境资源限制、旧进程停止机制，以及第 26 章的业务幂等与结果核实。

## 4. 取消以数据库提交顺序决定竞态

```text
queued ──领取──→ running ──完成事务──→ succeeded
   │                 │
   └─取消→ cancelled └─取消→ cancel_requested
                                    │
                         Worker 确认或租约到期
                                    ↓
                                cancelled
```

运行中取消先提交时，状态变为 `cancel_requested`，后续完成、产物发布和心跳都被拒绝。有效租约仍占并发名额，直到 Worker 确认停止或到期，防止刚提出取消就立即放入更多工作。到期清理由下一次 `claim()` 触发；该任务不会被重新派发。实际服务应有周期回收器，本实验不启动后台定时器。

完成事务先提交时，后来的取消返回 `too_late`，保留成功状态与产物。这是单个数据库边界内的确定规则；取消不会删除已交付产物，也不能回滚外部业务动作。实验不实现子任务，因而没有取消后的派生 API；真实调度器要在创建子任务时再次检查父 Run 的取消和租约条件。

## 5. 小产物与成功状态在同一事务提交

演示先在独立 `TemporaryDirectory` 写 `draft.md`，再将内容交给 `complete()`。正式报告以最多 64 KiB 的 SQLite BLOB 保存，并在同一事务中把 Run 标为 `succeeded`；产物 ID 和摘要由服务端产生，下载名固定为 `report.md`。`complete()` 不接收任意路径或客户端存储键，没有覆盖已有产物的 API。

这样可以专注验证：临时工作区与正式产物生命周期分离，完成状态与产物引用不能只成功一半。测试通过数据库触发器注入完成更新失败，确认之前插入的产物也被回滚。

**这是小文件教学简化。** 生产中的大文件通常放入对象存储，SQL 保存元数据与稳定引用。SQL 事务不能原子提交对象存储上传，需要设计候选对象、已提交清单、校验、幂等引用提交和未引用对象回收；不要把本实验的原子性扩展到两种存储。此处没有跨数据库／文件的正式产物提交，也不需要实现孤儿对象清理。

## 覆盖范围与练习

18 项测试覆盖：重启后找回同一 Run、请求指纹冲突、同租户其他用户的键冲突不泄露信息、跨租户同键独立、Session/Run/产物归属、并发争领与重复唤醒、租户并发隔离、过期回收与 epoch 防回写、未回收前过期写入拒绝、心跳续期、排队取消、运行取消与名额保留、过期取消不重派、完成与取消竞态、产物与状态事务回滚、工作区销毁与重开数据库后下载、积压满额与输入／产物上限。

可以继续做三个练习：

1. 把 `max_active` 设为 2，同时接收 3 个任务，竞争领取并观察有效租约上限；思考 CPU 池和供应商并发额度为何还要单独限制。
2. 在 `complete()` 前后分别请求取消，画出两种事务提交顺序与界面应展示的状态。
3. 将正式产物换成对象存储，列出上传成功但元数据未提交、元数据提交后 Worker 丢回执、对象清理与提交并发三种故障的处理协议，再实现；不能直接复用 SQLite BLOB 的原子性结论。

本实验未实现 HTTP／认证、租户角色与共享权限、真实队列 ACK、Outbox、跨主机数据库、定时与事件触发、公平调度、优先级、重试预算、死信、检查点、外部副作用、真正的后台进程、进程停止、对象存储、版本分享、保留与到期清理、监控和迁移。SQLite 的写事务串行化使本实验容易验证，不能据此证明多主机吞吐量或高可用能力；不要将数据库放在网络共享文件系统后当作分布式协调器。调度限额保存在进程配置，真实部署还要保证所有 Worker 使用一致且可审计的配额来源。
