# 第 33 章实验：把“改完代码”推进到“证据可审查”

这个离线实验实现一个很小的可信验收 Harness。案例是企业工单服务的权限缺陷：旧实现只检查租户，导致员工能够读取同租户其他员工的工单；候选修复必须从可信调用者得到租户和用户身份，同时满足租户隔离与工单所有权两个不变量。

实验只使用 Python 3.11+ 标准库，所有人员、租户、工单和版本号都是合成数据。它不联网、不调用模型、不读取真实仓库，也不会导入或执行候选工作区中的 Python 文件。

## 运行

在项目根目录执行：

```bash
python3.11 examples/ch33-coding-agent/lab.py demo
python3.11 -m unittest discover -s examples/ch33-coding-agent -p 'test_*.py' -v
```

`demo` 只向标准输出打印 JSON。实验在系统临时目录中创建固定教学文件，进程结束后自动清理；输出中的源码产物路径都是相对于临时工作区的路径。

## 先观察五种结果

| 场景 | 预期状态 | 为什么 |
| --- | --- | --- |
| `faulty` | `known_baseline_failure_reproduced` | 外置断言重现“同租户他人工单可见”；基线已带此缺陷，所以不能伪装成候选引入的新回归 |
| `fixed` | `ready_for_review` | 只修改获准的服务文件，受保护测试未改，四个外置验收场景全部通过 |
| `test_tamper` | `policy_rejected` | 候选同时弱化了受保护测试；在功能验证前被门禁拒绝 |
| `out_of_scope` | `policy_rejected` | 候选额外修改依赖声明，超出本任务允许范围 |
| `environment_failure` | `blocked_environment` | 合成工具链不可用；这是验证环境受阻，不是产品行为失败 |

演示最后会在 `fixed` 产生回执后再次修改源码。旧回执的源码树摘要不再匹配，`stale_evidence.valid` 为 `false`。这说明“某次测试通过”只能证明当时那棵源码树，不能自动证明之后的文件、其他提交或部署版本。

## Harness 做了什么

`AcceptanceHarness.assess()` 按固定顺序执行以下门禁：

1. 检查验证环境是否可用；不可用时返回 `blocked_environment`，不猜测产品对错。
2. 核对候选是否基于任务合同指定的 `base_revision`。
3. 将当前内容树中的相对路径与文件字节和固定基线逐项比较，识别新增、删除和修改路径。
4. 限制只修改 `src/service.py`，并确认受保护的 `tests/test_access.py` 没有变化。
5. 只接受实验内置的两个已知源码模板；源码缺失、不是 UTF-8 或不匹配模板时，都生成 `reviewed_template=failed` 的结构化拒绝报告，不通过 `exec`、`import` 或子进程运行。
6. 用 Harness 内部的独立行为模型验证本人工单、同租户他人、跨租户和不存在四个场景。
7. 输出来源路径、SHA-256、每项检查状态和退出码，形成可机器读取的回执。

候选仓库里的 `tests/test_access.py` 只是用来演示测试资产保护。真正决定验收结果的是工作区外的 `run_external_suite()`；因此候选不能通过删除失败用例，把自己的结果改成成功。

四个验收对象经过刻意设计，使失败原因可以分开判断：调用者固定为 `tenant-a/alice`；`T-A2` 与调用者同租户但属于 `bob`，只缺所有权检查的实现会在这一项失败；`T-B1` 属于 `tenant-b`，但 `owner_id` 同样是 `alice`，只缺租户检查的实现会在这一项失败。本人工单防止实现用“全部拒绝”伪装安全，不存在工单则防止系统返回伪造对象。测试还用四个负向行为模型逐项证明，每个断言都能唯一击穿对应错误。

## 证据绑定

每份报告的 `evidence` 同时绑定五项内容：

| 字段 | 绑定对象 | 防止的误用 |
| --- | --- | --- |
| `tree_digest` | 内容树中所有相对路径和文件内容摘要 | 用 A 提交的测试结果证明 B 提交 |
| `base_revision` | 候选起点 | 在错误基线或过期分支上评审补丁 |
| `policy_digest` | 允许路径、受保护路径、变更数和套件 ID | 验证后悄悄放宽门禁 |
| `environment_digest` | 镜像、网络策略和 Harness 版本 | 把不同工具链的结果当成等价 |
| `check_suite_digest` | 外置验收套件合同和实现摘要 | 换一组更弱断言后复用旧结论 |

`verify_receipt()` 会重新计算这些字段，同时校验报告正文摘要。缺少任一字段、源码内容树后来变化、环境或策略变化、报告文字被改写，都会让回执失效。这里的“内容树”只覆盖相对路径和文件字节，不包含 Unix mode、所有者、扩展属性、inode 或时间戳。摘要提供的是内容绑定和误用检测；本实验没有数字签名、可信时间戳或防篡改存储，因此不能证明报告由某个真实主体签发。

## 退出码与完成边界

下表是每个场景报告里的 `report_artifact.exit_code`。`demo` 会一次聚合成功、失败和阻断场景；只要演示程序自身正常完成，它的进程退出码就是 `0`。

| 退出码 | 含义 |
| --- | --- |
| `0` | 本实验门禁通过，状态为 `ready_for_review` |
| `1` | 基线缺陷已重现、候选失败或政策拒绝 |
| `2` | 验证环境受阻，尚未得到产品结论 |

`ready_for_review` 只表示这个合成候选已具备人工评审所需的最小证据。它不授权合并，不代表 CI 全部通过，不表示已经部署，更不能替代真实用户或设备验收。企业流程还应分别记录合并者、发布审批、目标制品摘要、灰度指标和业务验收回执。

## 主要接口

| 接口 | 职责 |
| --- | --- |
| `write_workspace(root, scenario, base_revision)` | 在指定临时目录写入固定的教学候选 |
| `snapshot(root)` / `tree_digest(files)` | 枚举全部内容路径并生成稳定的路径与内容摘要 |
| `changed_paths(files)` | 将候选与固定基线比较，列出真实变更路径 |
| `run_external_suite(variant)` | 在 Harness 内执行四个独立业务断言 |
| `AcceptanceHarness.assess(workspace, environment)` | 应用环境、基线、范围、测试完整性和功能门禁 |
| `AcceptanceHarness.verify_receipt(report, workspace, environment)` | 验证回执仍与当前源码、策略、环境和检查套件一致 |
| `demo()` | 输出四类候选、环境故障和过期证据的完整示例 |

## 工程边界

这是为了看清验收逻辑而做的单进程教学模型，不是通用代码执行平台：

- 源码模板和行为模型都预先写在 Harness 中，只能评估四个固定场景，不能判断任意 Python 补丁的真实语义。
- 临时目录不是安全沙箱；真实系统需要容器或虚拟机边界、只读基线、网络和凭据控制、资源配额，以及执行结束后的可靠回收。
- `snapshot()` 没有冻结并发写入，也没有在读取前后核对文件元数据；文件在枚举与读取之间变化时可能形成混合视图。真实系统应先取得不可变快照，再在该快照上验证。
- 内容树摘要不覆盖文件 mode、所有者和扩展属性；若执行权限或文件权限属于交付合同，应把规范化权限清单也绑定进证据。
- `base_revision` 是合成字符串，没有读取真实 Git 对象，也没有证明工作区确实来自该提交。真实系统应绑定不可变提交、依赖锁文件和实际 checkout 摘要，并防止 checkout 与验证之间发生竞态。
- 没有真实身份认证、审批、签名、CI、代码所有者规则、分支保护、制品仓库、部署或回滚。
- SHA-256 只能证明内容是否一致，不能证明内容正确，也不能证明报告签发者可信。
- 四个断言只覆盖这个教学缺陷。真实任务还需要按风险增加单元、集成、契约、迁移、并发、性能、安全和实际使用路径验证。

实验刻意把“候选生成”“可信验证”“人工评审”“合并发布”和“生产验收”分开。企业级 Coding Agent 的价值不只是写出补丁，而是让每一步的输入、权限、证据和完成状态都能被后续责任人复核。
