# 第 24 章实验：打断、播放准入与业务回执

员工让设备报障助手创建工单，助手正在播报时员工说“等等”。应该立即停止旧语音；如果创建请求已经发出，就继续核实那一次写入的回执。重新连接后，不能再播旧连接的音频，也不能再提交一次工单。

这个离线实验使用 Python 3.11 标准库，在内存中模拟上述控制规则。音频帧只包含身份、序号和时长，不包含真实音频；工单写入只增加计数，不访问任何业务系统。

## 运行与预期结果

在本目录执行：

```bash
python3.11 voice_lab.py
python3.11 -m unittest -v
```

演示输出：

```text
1 生成结束：generation_done
  播放确认：playback_completed
2 用户打断：queued_ms=0，迟到音频=stale_ignored
3 连接重建：epoch=2，旧连接音频=stale_ignored
4 队列溢出：buffer_overflow，queued_ms=0
5 写入结果：dispatched_unknown
  打断后：reconciling
  重连重试：not_dispatched_again
  只读核实：confirmed
  dispatch_count=1，receipt_id=ticket-8042，cancel_status=too_late
```

## 1. 把一段音频绑定到正确的回复

`StreamKey` 包含 `session_id`、`connection_epoch`、`turn_id`、`response_id`。Session 由服务端认证与会话服务绑定；`connection_epoch` 表示连接代次；`turn_id` 表示对话轮次；同一轮中不同的回复使用不同 `response_id`。

`Player.bind_response(key)` 只能由可信会话控制器调用；它先核对当前 Session、连接代次和轮次，再建立当前回复。媒体包只携带已有绑定，不能通过发送一个新的 ID 为自己获得播放权限。本实验的 `key()` 是可信控制器的便捷构造器，不是客户端身份认证接口。

| 方法 | 模拟的职责 | 关键约束 |
| --- | --- | --- |
| `bind_response(key)` | 为当前轮次安装回复 | 拒绝旧代次、旧轮次、其他 Session、当前代次与轮次内重复使用的回复 ID |
| `offer(frame)` | 接收适配器转换后的顺序音频帧 | 四个身份字段匹配、序号连续、时长合法、预算足够 |
| `take_next(key)` | 将一帧交给音频输出设备 | 只接受当前回复；交给设备不代表已经播放 |
| `ack_played(key, offset_ms)` | 收到该回复的累计播放位置 | 单调不减，不能超过已交给设备的音频时长 |
| `generation_finished(key, last_seq)` | 模型或 TTS 已生成结束 | 必须收到完整帧序列；仍要等实际播放确认 |

`offer()` 对相同序号、相同时长的重复帧返回 `duplicate_ignored`，不会重复计入预算。相同序号却不同时长会终止回复。真实协议还需要检查音频内容指纹、流格式与时间轴一致性，这里只模拟元数据重复。

教学传输合同要求适配器向 `Player` 提供连续顺序的帧。出现序号缺口时，实验立即终止本回复，不能把缺失前后的片段拼起来继续播。真实 RTP 接收端通常先做乱序恢复、抖动缓冲与丢包隐藏，不能直接照搬这里的“缺口即终止”作为 RTP 算法。

## 2. 生成完成与播放完成分别记账

每个 `Response` 分别记录四个量：

- `received_ms`：当前回复已经通过准入并接收的总时长。
- `queued_ms`：仍在应用播放队列中的时长。
- `submitted_ms`：已经交给模拟音频输出设备的总时长。
- `played_ms`：输出设备确认已经播放的累计时长。

例如，接收 40 ms 音频并收到 `generation_finished()` 时，`generation_done=True`，但音频可能还在队列中。`take_next()` 之后，它只到了输出设备；直到 `ack_played(key, 40)`，才得到 `playback_completed`。

这里的播放确认是可信输出适配器提供的模拟数据。浏览器或硬件回调只能给出其能力范围内的播放位置估计；它不能证明员工真的听见、听懂或同意了内容。

## 3. 先停止本地播放，再请求远端取消

`interrupt()` 同步把当前回复标为已停止，并清空本地队列。随后即使旧生成任务的音频、生成结束或播放确认回调迟到，也只能得到 `stale_ignored`，不再更新当前播放状态。真实系统仍可按旧回复身份记录停止前后确认的播放位置，用于审计和历史对齐，但这些确认不能推进新回复；本实验没有实现旧回复播放位置的保留机制。`new_turn()` 推进轮次，`reconnect()` 推进连接代次；两者都清空旧回复，之后必须显式绑定新回复。

真实播放器还必须停止正在播放的 AudioBufferSource、音频设备队列或硬件缓冲。本实验没有这些设备，只能证明应用队列和迟到回调的控制规则正确。远端取消、会话历史截断和实际播放位置同步也需在供应商适配层实现。

`max_buffer_ms` 限制应用队列的累计时长，演示默认 120 ms。这是便于观察的实验数字，不是生产推荐值。溢出时返回 `buffer_overflow`，停止并清空整个回复，后续帧不再接收；不会静默丢掉中间一帧后继续播剩余内容。

实验额外限制每次回复最多 30 秒、每帧 1—200 ms、每个连接代次与轮次组合最多绑定 16 个回复，避免用于序号去重的容器在持续消费时无限增长。真实系统应给音频设备队列、网络发送队列和解码缓冲分别设置预算，不能把本实验的应用队列上限当成端到端播放积压上限。

## 4. 业务写入与媒体打断分开处理

`OperationLedger` 模拟可信业务执行层。`prepare(operation_id, approved_payload)` 将操作 ID 绑定到已批准的正文；这里假定身份、权限和审批已经由外部系统完成。`dispatch()` 模拟发出一次创建请求，但没有拿到回执，因此状态为 `dispatched_unknown`。

此时 `request_stop()` 进入 `reconciling`。再次调用 `dispatch()` 得到 `not_dispatched_again`；只能通过 `query_receipt()` 查询原操作。没有回执就保持核实中，得到 `ticket-8042` 后才进入 `confirmed`，取消结果为 `too_late`。已确认的回执不会被后来的停止请求或空查询覆盖。

若操作仍为 `prepared`，停止请求会将其标为 `cancelled`，之后不能派发。相同操作 ID 若绑定不同正文或冲突回执，实验会拒绝处理。新建另一个操作 ID 代表另一个操作，不能用它绕过原操作的未知结果。

本实验不把“语音被打断”自动解释为“用户撤销业务操作”。演示分别调用 `Player.interrupt()` 与 `OperationLedger.request_stop()`，用来观察两种控制的不同结果。真实产品必须先确定员工这句“等等”的业务意图；即使明确请求停止，也需要按照原操作真实状态处理。

## 测试覆盖与实践练习

17 项测试覆盖跨 Session 和同轮不同回复、回复替换、旧连接和旧轮次、重复和冲突音频帧、序号缺口、队列溢出、打断后迟到回调、生成结束与播放结束的区别、播放位置单调性和上界、回复总时长预算，以及未知写入核实、取消前后回执保留与正文版本绑定。

可以做三个小实验：

1. 把队列预算设为 100 ms，先接收 80 ms，再接收 40 ms；观察整条回复如何停止，而不是只丢掉第二帧。
2. 先接收并取出 40 ms 音频，依次确认播放位置 20、19、41、40；理解为什么中间两个确认会被拒绝。
3. 在业务派发前后分别停止，再模拟无回执和有回执；确认只有派发前停止能安全得到 `cancelled`，已经派发的未知写入始终围绕原 `operation_id` 核实，可以重复查询，不得重新派发写入。

## 接入真实系统前需要补齐的能力

本实验没有实现麦克风采集、编码解码、重采样、ASR、VAD、AEC、TTS、WebRTC/WebSocket、网络背压、真正的音频输出、客户端认证、租户隔离、供应商事件协议、业务审批、持久化日志、事务 Outbox、跨进程 fencing、真实幂等接口或崩溃恢复。它不测量真实延迟，也不能证明双工硬件效果。

`OperationLedger` 的操作表保存在内存，进程退出就丢失。它只能演示单进程中“不因媒体重连而重派”的规则；要跨进程重启保持该规则，需要在派发前持久化操作身份和派发状态，并按业务接口的幂等与对账能力实现恢复。业务记录与回执的保留周期应由服务端存储规则管理。
